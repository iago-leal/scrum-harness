# Estratégia de testes

Este documento diz como as regras de RULES.md (v5) e os contratos de API_SPEC.md (v2) são provados no vocabulário de GLOSSARY.md, sobre a divisão M/V/C de ARCHITECTURE.md. A suite real é vitest: 18 arquivos, 510 testes, `node node_modules/vitest/vitest.mjs run` em ~2,2 s numa máquina de desenvolvimento; o orçamento deste quadro é 10 s (R28). Não há cobertura por linha configurada e nenhuma porcentagem é prometida: **o critério de cobertura é por regra** — toda regra R/S/P que o código impõe tem ≥ 1 caso crítico abaixo; as marcadas "convenção da casa, não gate" não têm prova de código e são listadas em «O que NÃO testar». Uma cláusula sem asserção na suite é marcada **a escrever** ao lado dela, nunca escondida atrás de uma prova vizinha.

## Níveis

**(a) Unitários puros — Model e View, sem storage.** Funções e classes sem estado, chamadas diretamente:
- contratos (`contracts.spec.ts`): `ArtifactContract`, `RequirementsContract`, `ReviewContract`, `ValidationContract`, `SuiteBudget`, `TraceContract`, `TraceMatrix`, `TitleContract`, ids de requisito, `normalizePath`/`matchPath`, `gitignoreNames`, a constante `TRACE_PROBE_CAP`;
- parser de frontmatter da casa (`frontmatter.spec.ts`);
- catálogo e contratos de spec (`specs.spec.ts`): `SpecCatalog`, `SpecContract`, `SpecReviewContract`, `SpecSet.of` sobre uma sonda fabricada em memória, `SPEC_PREDECESSORS`, `SpecOrder.gate`, `SpecBrief.of`, `SpecReviewBrief.of`;
- View texto (`format.spec.ts`): `formatTree`, `formatSprints`, `formatSuiteBudget`, `formatTraceMatrix`, `formatImpact`, `formatReviewBrief`, `formatSpecStatus`, `formatSpecBrief`, `formatSpecReviewBrief`, `withBoardHeader`, sobre dados fabricados;
- View browser sem DOM (`packages/ui-scrum/tests/{form,markdown,mermaid,mermaid-engine,settle,side,drag}.spec.ts`): rodam em Node sem jsdom, testam as funções puras (`phaseSteps`, `checklist`, `artifactPatch`, `splitFrontmatter`, `mermaidBlocks`, `createSettler`, `createSwitch`, `clampPlacement`); o adaptador do mermaid recebe `document` e a lib por parâmetro (stubs).
- `context-scrum` **não** está aqui: alguns `it` são puros (`renderSprintContext` sobre stub — «(stub board)», «via stub» — e a `hygiene line (comp-54 R3)`), mas o arquivo monta um `Context` real sobre o backend em memória e conta inteiro no nível (b).

**(b) Integração — o Model real sobre storage real, em memória.** `ScrumBoard` atravessa hub `dsh-storage` + `storage-domain` reais com o backend `memory` de `test-support` (ADR-002): um `Context` por arquivo, um quadro por teste (`beforeEach` abre um nome novo; os ids recomeçam em `rel-1`). Em cima dele: `scrum-domain.spec.ts` (o serviço e os gates), as tools via `run(name, args, { cwd })` (`tool-scrum.spec.ts`), a API HTTP via servidor real e `fetch` (`scrum-api.spec.ts`), o `/scrum` (`command-scrum.spec.ts`) e o listener `agent/pre-step` mais o snapshot (`context-scrum.spec.ts`). Exceções deliberadas: os `describe('persistence…')` de `scrum-domain.spec.ts` usam o backend JSON num `mkdtemp`, porque durabilidade (close/reopen, migração persistida) é o que eles provam; a sonda (`probe.spec.ts`) lê um diretório temporário real; `repo-specs.spec.ts` é o **único** arquivo que lê o disco do repositório (`<repo>/specs/`).

**(c) E2E — a GUI viva.** `scripts/e2e-side.mjs` (Playwright do checkout do DSH, fora do vitest): abre a GUI em `http://127.0.0.1:3090`, liga a cápsula «▦ SCRUM», confere a coluna `details`, o poll por visibilidade e o work item form, imprimindo `PASS`/`FAIL` por passo. Roda à mão após `npm run bundle -w @scrum-harness/ui` (o script `bundle` = `node build.mjs` existe só em `packages/ui-scrum/package.json`, não na raiz; o comentário de `scripts/e2e-side.mjs` ainda diz `npm run bundle` e deve ser corrigido junto); as linhas vão coladas no corpo do artefato `validation` do componente que tocou a GUI. Não conta em `suite.tests`.

**Como cada nível é medido.**
- vitest: `npm test` (= `node node_modules/vitest/vitest.mjs run`, `package.json`; o caminho é longo porque `.npmrc` traz `bin-links=false` e `node_modules/.bin` fica vazio — `npx vitest` não resolve) é a suite; `tests`, `passed`, `skipped` e `wall_seconds` do artefato `validation` vêm dela.
- typecheck: `npm run typecheck` (= `node node_modules/typescript/bin/tsc --build`, build real e incremental dos projetos compostos) sem erro é o `typecheck: clean` do artefato; `tsc --build --dry` só lista o que construiria, não verifica tipos e não vale como evidência.
- gate de `done` (R26, P1): o artefato traz `suite.runs` com ≥ 3 rodadas consecutivas, a **pior** em `wall_seconds`, `budget_seconds ≤` orçamento do quadro (10 s); o gate confere forma e aritmética, não executa a suite (trade-off declarado em ARCHITECTURE.md).
- vermelho por desenho: `repo-specs.spec.ts` foi escrito antes das specs (TDD) e é o critério de aceitação da rel-21 (C4). Tem dois `it`: «exists and is complete…» exige os três mínimos `approved` sem `invalid`/`unknown` e **já passa**; «the seven files of the pipeline…» exige PRD, GLOSSARY, RULES, ARCHITECTURE, API_SPEC, TESTS_SPEC e AGENTS `approved` com revisão `current` e para no primeiro que falha. Enquanto este arquivo e AGENTS.md forem `draft`/ausentes, a suite reporta **1 falha** esperada (509/510), nesse `it` e em nenhum outro arquivo; até ela sumir, nenhum artefato `validation` desta release fecha `passed + skipped = tests` — a comp-61 não vai a `done` antes do carimbo.

## Casos críticos

Formato: `CT-nnn — caso (valida <regras>; prova: <arquivo> › <describe>)`. Arquivos citados pelo nome curto: `scrum-domain`, `contracts`, `specs`, `format`, `frontmatter`, `repo-specs` (em `packages/scrum-domain/tests/`), `probe` (`packages/scrum-probe/tests/`), `tool-scrum`, `scrum-api`, `command-scrum`, `context-scrum`, e os de `ui-scrum`. "a escrever" = cláusula ainda sem asserção na suite (o código existe; o teste não).

### Hierarquia, ids e títulos
CT-001 — Criar os quatro níveis gera ids curtos e sequenciais; filho de pai inexistente é `not-found` (valida R4, R5; prova: scrum-domain › hierarchy «creates the four levels», «rejects children of missing parents»).
CT-002 — Um item na lixeira recusa exclusão, edição e reseleção em sprint com `in-trash`; filho novo sob pai inexistente é `not-found` (valida R5, R16; prova: scrum-domain › trash «guards» — `deleteItem`/`updateItem`/`planSprint` sobre a tarefa na lixeira e `createTask` sob `comp-9`). Filho novo sob pai **na lixeira** (`in-trash`) ou **arquivado** (`archived`): a escrever — nenhum teste cria filho sob pai na prateleira (código: `mustGetLive`, `service.ts`).
CT-003 — Cada nível caminha o próprio workflow; estado fora do conjunto é `invalid-status` (valida R6; prova: scrum-domain › workflows (multi-level states), › hierarchy «updates by id prefix»). Concluir a última tarefa não move a fase: scrum-domain › phase readiness (comp-46 R1) «…each expose their gate» — após `finish([early.id])` a readiness segue `{ phase: 'construction', next: 'validation', ok: true }`; criar tarefa depois de `done` não desfaz `done`: › done gate «only the transition is gated». Que o `status` do componente siga `in_progress` ao concluir a última tarefa: a escrever.
CT-004 — Título de 81 code points ou meta de 121 é `title-contract` com a mensagem literal nas sete escritas (create ×4, `updateItem`, `planSprint`, meta) (valida R7; prova: scrum-domain › title contract — where the gate bites; contracts › TitleContract).
CT-005 — Quebra de linha ou controle (`\n`, `\r`, `\t`, U+007F, U+0085, U+2028) é recusado; controle e comprimento vêm juntos, controle primeiro (valida R2, R7; prova: contracts › TitleContract).
CT-006 — O comprimento conta code points (emoji astral = 1, família ZWJ = 5); o contrato mede o título gravado, já sem o prefixo `[test]`/`[code]` e trimado; vazio ou só-espaços é `invalid-input` (valida R7, R9; prova: contracts › TitleContract; scrum-domain › title contract «measures the stored title», «empty stays invalid-input»).
CT-007 — Uma criação ou `planSprint` recusados nunca consomem id nem número de sprint: o próximo id é consecutivo (valida R4; prova: scrum-domain › title contract «never burns a counter»; › task kind «without consuming an id»; tool-scrum › title contract (comp-53)).
CT-008 — Mídia legada com título > 80 e meta > 120 abre; `tree()`/`sprints()` anotam `titleOverflow`/`goalOverflow` só no item em excesso, nunca persistidos; toda escrita que não toca título passa; reenviar o mesmo título longo é recusado; encurtar limpa a anotação (valida R8; prova: scrum-domain › title contract — legacy read, marked, never rejected).
CT-009 — A faixa de aviso começa em 64 (título) e 96 (meta): `tone` responde ok/warn/over (valida R8; prova: contracts › TitleContract.tone).
CT-010 — Kind explícito, inferido do prefixo ou `other` por default; o título armazenado nunca carrega o prefixo; `[test] x` com `kind: code` é `kind-conflict`; título só-prefixo é `invalid-input`; kind fora do conjunto é `invalid-kind`; `updateItem` com prefixo move o kind (valida R9; prova: scrum-domain › task kind (comp-45); tool-scrum › task kind tools; scrum-api «createTask/updateItem accept kind»).

### Sprint e Kanban
CT-011 — Só uma sprint `planned` começa quando nenhuma está ativa (`sprint-already-active`); iniciar não-`planned` ou encerrar não-`active` é `invalid-transition` (valida R10; prova: scrum-domain › sprints «allows at most one active sprint»; scrum-api «maps business errors onto 404/409»; o `invalid-transition` explícito: a escrever).
CT-012 — Encerrar a sprint devolve ao backlog toda tarefa não `done` (sem `sprintId`) e preserva o vínculo das `done` (valida R11; prova: scrum-domain › sprints «plans, starts, moves on the board, and ends returning unfinished tasks»); a sprint fica `completed`: scrum-api «runs a full flow through POST actions» (`result.sprint.status`); `endDate` preenchida ao encerrar: a escrever — nenhum teste lê `endDate`.
CT-013 — Entrar e sair só de sprint não `completed`; entrar duas vezes é `task-already-in-sprint`; sair devolve ao backlog e apaga `doneAt` (valida R12; prova: scrum-domain › sprints «assigns and removes tasks from a planned sprint», › burndown & wip; `sprint-completed` explícito: a escrever).
CT-014 — Mover só na sprint ativa e só para as quatro colunas; fora dela é `task-not-in-active-sprint`; entrar em `done` carimba `doneAt` (mantido se já havia) e sair o apaga (valida R13; prova: scrum-domain › sprints «rejects board moves», › burndown & wip «stamps doneAt»).
CT-015 — WIP limits: chaves entre as colunas (`invalid-column`), inteiros ≥ 0 (`invalid-input`), 0 remove a coluna, `{}` remove o campo; um movimento acima do limite nunca é bloqueado (valida R14; prova: scrum-domain › burndown & wip «validates and stores per-column WIP limits»; o "nunca bloqueia": a escrever).
CT-016 — Uma sprint vincula várias releases (`releaseIds` substitui o conjunto, `releaseId` é atalho, `""` desvincula; id de release inexistente é `not-found`); release na lixeira mantém o vínculo, só purge desvincula (valida R18 na parte do purge; prova: scrum-domain › sprints «links one sprint to MANY releases», «trashing a release keeps sprint links»). A validação de `releaseIds` contra releases vivas não tem regra própria em RULES.md (R5 é a hierarquia, não o vínculo sprint→release): lacuna a propor ao Domain Analyst.
CT-017 — Cerimônia grava contra a sprint ativa por default, lista em ordem, exige ≥ 1 nota e sprint explícita quando nenhuma está ativa (`not-found`); `spr-`/`cer-` em delete/archive é `invalid-id` (valida R15; prova: scrum-domain › ceremonies; o `invalid-id` de `spr-`/`cer-`: a escrever).

### Lixeira, arquivo e purge
CT-018 — Excluir é soft delete: o item sai da árvore, aparece na lixeira e restaura; pai com filhos vivos é `has-children` sem `cascade` e vai inteiro com `cascade` (valida R16, R17; prova: scrum-domain › trash «soft deletes», › hierarchy «refuses non-cascade deletion»).
CT-019 — Restaurar revive os ancestrais na prateleira e os descendentes excluídos pelo mesmo carimbo, como uma unidade (valida R17; prova: scrum-domain › trash «restores a cascade as one unit»).
CT-020 — Purge só de item na lixeira (`not-in-trash`), físico e com a subárvore na lixeira; `emptyTrash` esvazia de uma vez (valida R18; prova: scrum-domain › trash «purges only from the trash», «empties the whole trash»).
CT-021 — Tarefa da sprint ativa não vai à lixeira nem ao arquivo (`task-in-active-sprint`, também via cascade do pai); tarefa não `done` excluída sai da sprint planejada e volta ao backlog (valida R19; prova: scrum-domain › trash «guards», «trashing a not-yet-done task drops it from its planned sprint»; › archive «archived done tasks keep counting»).
CT-022 — Arquivar exige vivo (`already-archived`); tarefa `done` arquivada continua contando nos totais da sprint encerrada e nos gates; lixeira vence arquivo (excluir apaga `archivedAt`) (valida R16, R20; prova: scrum-domain › archive «archives concluded work», «archived done tasks keep counting», «trash wins over archive»). Desarquivar item não arquivado é `not-archived`: a escrever — nenhum teste contém a string (código: `unarchiveItem`, `service.ts`).
CT-023 — Item na lixeira ou arquivado recusa mutação de conteúdo e de fase com `in-trash`/`archived`; readiness e matriz recusam por nome (valida R16; prova: scrum-domain › spiral phases «refuses setPhase on a done component and on shelved ones»; › phase readiness «shelved components refuse»; › impact «refuse trashed»).
CT-024 — As tools da lixeira e do arquivo e as rotas HTTP fazem o ciclo completo (delete → list → restore → purge; archive → list → unarchive → archiveCompleted) e a prateleira leva `taskKind` (valida R1, R16–R20; prova: tool-scrum «drives the trash and the archive»; scrum-api «round-trips the trash and the archive over the wire»).

### Espiral e gates
CT-025 — Componente nasce em `requirements` com `phaseLog: []`; o primeiro avanço de `proposed` o torna `in_progress`; cada movimento (recuo incluído) acrescenta uma entrada ao `phaseLog` (valida R21; prova: scrum-domain › spiral phases (R1, R2, R7), › spiral gates «appends one phaseLog entry»).
CT-026 — Nunca pula; recua livre; mesma fase é no-op; avançar de `validation` é `phase-gate`; componente `done` não move fase; o erro traz o `code` e nomeia as duas fases (valida R2, R21; prova: scrum-domain › spiral gates «never skips forward», «gate errors carry the ScrumError code»).
CT-027 — `requirements → design` exige os dois artefatos e todo o contrato da revisão, nomeando cada razão; carimbar `approved` depois da revisão não a invalida (digest é do corpo) (valida R2, R22, R30; prova: scrum-domain › review contract gate (comp-48), › review contract — the digest property).
CT-028 — `RequirementsContract` recusa versão string ou fracionária, ausência do carimbo e corpo só-frontmatter; `ReviewContract` nomeia as condições na ordem fixa a → f, com o caminho do campo, e um digest só-dígitos precisa de aspas (valida R2, R22, R30; prova: contracts › RequirementsContract, › ReviewContract «an all-digit digest must be quoted»).
CT-029 — Digest é sha1 curto do corpo trimado, normalizando CRLF e linhas em branco iniciais; a revisão fica stale só quando versão ou digest divergem, nunca sem frontmatter válido (valida R30; prova: contracts › ArtifactContract base, › ReviewContract «stale»).
CT-030 — `design → tdd`: design vazio é exatamente `design is empty`; preenchido precisa da matriz com toda razão nomeada: ids sem rastro, ids desconhecidos, `req` vazio, caminho absoluto/`..`/com espaço; `files: []` cobre; `tests: []` fica unproven sem bloquear (valida R23; prova: scrum-domain › trace gates (comp-49 R4); contracts › TraceContract, › normalizePath / pathIssue / matchPath).
CT-031 — Ids `R<n>[letra]` são lidos só no início de linha do corpo, nas seis formas markdown, dedupados em ordem; menções no meio da linha e o `ids:` do frontmatter não contam (valida R23; prova: contracts › requirement ids (comp-49 R2)).
CT-032 — `tdd → construction`: sem tarefa, só `other`, sem `test`, e `code` criada antes da primeira `test` (ordem pelo número do id, `task-9` antes de `task-10`) são nomeadas; lixeira não conta, arquivada conta (valida R24; prova: scrum-domain › tdd gate (comp-45 R3); tool-scrum «the tdd gate refusal names the tests-first rule»).
CT-033 — `construction → validation` exige toda tarefa não-lixeira `done`; arquivadas `done` contam; um único item na lixeira deixa o denominador (valida R25; prova: scrum-domain › spiral gates «construction → validation needs every non-trashed task done», «trashed tasks leave the denominator»).
CT-034 — `status: done` é recusado fora de `validation`, sem tarefa concluída ou sem artefato válido, todas as razões juntas; aceito com tudo em ordem; avaliado no estado *next* (artefato e status no mesmo patch); `done → done` é no-op; sair de `done` e voltar é gateado de novo (valida R2, R26, R27; prova: scrum-domain › done gate (comp-47)).
CT-035 — `ValidationContract`: campos faltantes com caminho, `tests ≥ 1`, `passed + skipped = tests`, `typecheck: clean`, `wall ≤ budget_seconds ≤ orçamento`, `validated_at` é string ISO-8601 estendida (`AAAA-MM-DD` ou data-hora), lida pelo parser da casa como string com ou sem aspas (`2026-09-02` nu passa); um valor só-dígitos como `2026` é recusado de qualquer forma — nu, o parser o lê como número (mensagem «must be a quoted ISO-8601 date»); entre aspas, `ISO_DATE` exige os hífens (o `it` prova `'Jan 5'` e `2026` nu; `"2026"` entre aspas literal: a escrever) —, só-frontmatter não é evidência (valida R26; prova: contracts › ValidationContract (comp-47 R1, R2) «validated_at must be an ISO-8601 date»).
CT-036 — `suite.runs`: lista inline parseada pelo parser da casa; a pior rodada conta; `wall_seconds` diferente da pior (maior ou menor) é recusado com `≠`; menos de 3 rodadas é recusado; `overBudget` acompanha a recusa (valida R26, P1; prova: contracts › ValidationContract runs (comp-50 R1) and overBudget).
CT-037 — A matriz efetiva do `done` é o as-built da validação quando ela traz `traces:` (array, vazio incluído), senão o design; fecha sobre os ids ATUAIS dos requisitos; sem fonte alguma o gate fala do design (valida R23, R26; prova: scrum-domain › trace gates «the effective matrix closes against the CURRENT ids», «without any source»; contracts › TraceMatrix «the effective source»).
CT-038 — `phaseReadiness`/`doneReadiness` devolvem exatamente as razões que o avanço recusaria; `tree()` anota `readiness`, `readyForDone` e `traces` em todo componente na leitura, e `done` curto-circuita com `next: null` (valida R21, R26, R27; prova: scrum-domain › phase readiness (comp-46 R1), › done gate «tree() annotates readyForDone», › trace gates «tree() annotates traces»).
CT-039 — `scrum_component_phase check` lê sem mover nas quatro formas; `set` sem `phase` e `advance`/`check` com `phase` são recusados pelo envelope; `advance` e a API `componentPhase` traduzem o `phase-gate` intacto (valida R1, R21; prova: tool-scrum › phase check (comp-46 R4), «validates scrum_component_phase arguments»; scrum-api «drives phases and artifacts»).
CT-040 — `scrum_item_update` avisa sobre contrato de revisão, contrato de validação, matriz stale e gate que lerá o design, sem bloquear; e recusa `done` com todas as razões (valida R2, R26; prova: tool-scrum «warns about the review contract», «R6: warns about the validation contract», › scrum_item_update trace notes (comp-49 R8)).
CT-041 — `reviewBrief` devolve versão, digest, ids e frontmatter pré-preenchido e recusa por nome (`review-brief`) sem requisitos, sem `version` ou sem corpo; a View o renderiza em ordem fixa com os tetos de `TitleContract.limits()` (valida R2, R29, R30; prova: scrum-domain › review contract gate «reviewBrief returns the state»; format › formatReviewBrief, › review brief conventions — the title rule).

### Orçamento da suite e ids compartilhados
CT-042 — `scrum_suite_budget` lê o default 15, fixa um orçamento do quadro, recusa subir acima de 15 sem razão (também ao regravar o mesmo valor), recusa ≤ 0 ou não-número (`validation`), e 0 remove; o orçamento entra no gate de `done` (valida R28; prova: scrum-domain › suite budget (comp-50 R2) «reads the default…», «the board budget is injected into the done gate»; contracts › SuiteBudget; tool-scrum › suite budget tools).
CT-043 — Baixar o orçamento nunca reabre um componente `done`, mas `readyForDone` passa a refletir o novo teto (valida R28; prova: scrum-domain › suite budget «lowering the budget never reopens»).

## Pyramid alvo

A pirâmide real, contada pelos arquivos de hoje (510 testes):
- **Base — unitários puros (~60 %)**: `contracts`, `specs`, `format`, `frontmatter` e os sete de `ui-scrum`; rodam em milissegundos, sem storage nem DOM. Meta: manter ≥ metade da suite aqui — toda regra nova nasce como contrato ou função pura antes de ganhar um teste de integração.
- **Meio — integração sobre storage em memória (~40 %)**: `scrum-domain` (o maior arquivo), `tool-scrum`, `scrum-api`, `command-scrum`, `context-scrum` (inteiro, ver «Níveis»), `probe`, `repo-specs`. Meta: um teste de integração por superfície e por regra que atravessa o Controller (R1, S1, S2); nunca duplicar no Controller o que já está provado no Model.
- **Topo — e2e manual (1 roteiro)**: `scripts/e2e-side.mjs`, fora do vitest, rodado só quando a GUI muda; meta: continuar único e curto.

**Teto de tempo (convenção da casa e gate).** Pior de 3 rodadas consecutivas ≤ 10 s (orçamento do quadro, R28), reportada em `wall_seconds`; folga desejada: pior rodada ≤ 5 s, para que uma máquina 2× mais lenta ainda feche o gate. Hoje: ~2,2 s. Se a suite crescer além da folga, o remédio é mover prova do meio para a base, não subir o orçamento; subir exige razão gravada (`scrum_suite_budget`).

## O que NÃO testar

- Bibliotecas: `zod`, `marked`, `DOMPurify`, `mermaid`, Playwright, `dsh-storage`/`storage-domain`, `cordis` — só o que a casa configura em cima delas (a política do sanitizer, a grammar de fence, o `.transform` da mídia).
- O renderer do mermaid em si: só a grammar de fence (`mermaidBlocks`) e o pareamento por posição; o adaptador recebe a lib por parâmetro e é testado com stub.
- Cosmética da GUI: cores, tokens Primer, layout da coluna, screenshots — o e2e confere presença e sequência, não pixels.
- O LLM e os subagentes: os briefs (`formatReviewBrief`, `formatSpecBrief`, `formatSpecReviewBrief`) são testados como texto (blocos, ordem, frontmatter pré-preenchido), nunca o comportamento do modelo que os recebe.
- Cobertura por porcentagem de linhas: não há `coverage` configurado e nenhuma meta numérica é declarada; o critério é por regra (seção anterior).
- Convenções da casa sem gate (R29 identidade do carimbo, P1 trazer 3 rodadas, C1, C2, C3 no encerramento, C5 na revisão de desenho, a parte "toda migração nova" de R35): são disciplina de brief e revisão; o que delas o código impõe (forma do `runs`, `Higiene:` no snapshot) está nos CTs acima.
- Ausências de código: S4 (sem autenticação — toda chamada HTTP da suite roda sem auth; o isolamento por workspace é o CT-046) e "o quadro nunca escreve `specs/`" de R31 (não há caminho de escrita na sonda nem nas tools de spec; CT-068 prova só leituras).

## Dados de teste

- **Backend**: `packages/test-support/src/index.ts` registra o backend KV `memory` (`MEMORY_BACKEND`) no mesmo facet `kv` do hub; cada arquivo de suite monta um `Context` com `storage` + `storage-domain` + `test-support` + o plugin sob teste, e cada teste abre um quadro com nome novo (ids recomeçam em `rel-1`, `spr-1`).
- **Fixtures puras**: `packages/test-support/src/fixtures.ts` — `CONTRACT_REQ` (requisitos `version: 1`, `status: approved`, corpo `R1 — the component must work.`), `contractReview(digest)` (revisão aprovada cobrindo aquele digest), `CONTRACT_DESIGN` (matriz mínima `{ req: [R1], files: [src/a.ts], tests: [tests/a.spec.ts] }`), `specText(file, over)` e `specReviewText(file, { version, digest, … })` para fabricar specs e revisões válidas por default e quebrá-las campo a campo. Importam-nas `scrum-domain` e `context-scrum`; **exceção conhecida**: `tool-scrum.spec.ts` e `scrum-api.spec.ts` redefinem cópias locais `CONTRACT_REQ`/`CONTRACT_REVIEW` com outro corpo (`R1 — must work.`), e `scrum-domain.spec.ts` ainda tem `APPROVED_REQ`/`approvedReview` locais — unificar é dívida pequena, não bloqueio.
- **Diretórios temporários** (`mkdtemp` em `os.tmpdir()`): removidos no `afterEach` na sonda (`probe.spec.ts`), na matriz de impacto por caminho e no `specs/` fabricado (`tool-scrum.spec.ts`) e no backend JSON dos testes de persistência (`scrum-domain.spec.ts`); criados e removidos em `try/finally` dentro do próprio `it` no `specs/` da API (`scrum-api.spec.ts`) e do `/scrum` (`command-scrum.spec.ts`). Os workspaces dos quadros (`root`/`filePrefix` em `scrum-domain`, `tool-scrum`, `scrum-api`, `command-scrum` e `context-scrum`) são só prefixos de caminho — nomes de quadro para `boardNameOf`, nunca criados no disco.
- **O `specs/` deste repositório**: lido só por `repo-specs.spec.ts`, pela sonda real; nenhum outro teste depende do conteúdo destes arquivos.
- **Textos de artefato inline**: os frontmatters de `validation`/`design`/revisão usados nos gates são strings literais no próprio teste. Aspas em digest e data só importam quando o valor é só-dígitos (o parser da casa leria `12345678` ou `2026` como número — contracts «an all-digit digest must be quoted», «validated_at … a bare all-digit value must be quoted»); um digest só-dígitos entre aspas passa, uma data só-dígitos não passa nem entre aspas (`ISO_DATE` exige hífens, R26); nos demais casos a suite os deixa sem aspas (`VALID_VALIDATION` tem `validated_at: 2026-09-02`; `approvedReview`/`CONTRACT_REVIEW` e `contractReview` de `test-support` interpolam o digest hex sem aspas) — o contrato exige string ISO e o parser entrega string aí. `specReviewText` e os briefs pré-preenchidos sempre citam o digest entre aspas, porque não sabem se ele sairá só-dígitos (GLOSSARY «Frontmatter»).
- Nada de dados de produção: o JSON de `DSH_HOME/storages/` nunca é lido pela suite.
